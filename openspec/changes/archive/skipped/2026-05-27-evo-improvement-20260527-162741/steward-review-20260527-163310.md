## 疑虑

1. **没有具体变更计划**：proposal 连自己要改什么都不知道就要求执行。Technical Design 的四个步骤本质上是「去看看→找问题→改→测」，这不是技术设计，这是工作流的自然语言描述。没有任何函数名、接口变更、逻辑修改的细节。

2. **auto-generated 循环风险**：proposal 明确标注「由 zsiga 自演进引擎生成」。历史显示 `evo-improvement-20260527-125207` 几乎同一模式，在 verify 阶段失败。这类 proposal 的典型循环是：生成→执行→发现没问题可改或改了无关紧要的东西→verify 失败→再生成一个类似的。

3. **AC 形同虚设**：BAC-02 说「实施至少 1 项实质性改进（非格式化）」——谁来判断「实质性」？如果有人把一个变量名改了，这算不算实质性？没有客观标准意味着 verify 阶段必然产生争议。

4. **runner.py 是 harness 核心组件**：它包含 `HarnessRunner`、`_HarnessCollectorPlugin` 等关键类。模糊的「改进」可能引入回归，影响整个测试 pipeline。

## 建议

1. **先完成探索，再提 proposal**：先用 read-only 方式分析 `runner.py`，识别出 1-2 个具体问题（如「函数 X 缺少错误处理 Y」「逻辑 Z 可以简化为 W」），然后基于发现提交有具体变更目标的 proposal。

2. **将 AC 改为可自动验证的 Binary Check**：
   - 例如：`tests/test_runner.py` 中存在 `test_harness_runner_*` 且至少 3 个 testable cases
   - `zsiga/harness/runner.py` 中 `HarnessRunner.run` 方法包含 `except` 块（如果目标是加错误处理）
   - `pytest tests/test_runner.py` 返回 exit code 0

3. **避免 auto-generated 无目标循环**：自演进引擎生成 proposal 时，应先做静态分析确定具体问题，而不是生成「去探索」的空壳 proposal。
