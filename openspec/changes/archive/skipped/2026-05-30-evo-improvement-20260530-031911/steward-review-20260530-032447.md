## Verdict: PUSHBACK

## 我的判断

我强烈建议驳回这个 proposal——不是因为"给 config.py 加测试"这个想法不好，而是因为这个 proposal 建立在一个虚假的前提上。它声称 `zsiga/config.py` 缺少测试文件，暗示该模块未被测试覆盖，但实际上 **现有 7 个测试文件已经覆盖了约 90% 的公开函数**（约 50 个测试用例）。`test_config_validation.py` 一个文件就有 426 行、~30 个测试覆盖了 `validate_config`、`load_config`、各类 config 类。`test_spec_evo_..._config_unit_coverage.py` 已经覆盖了 `_find_config` 和 `_resolve_env_vars`。

更令人担忧的是：这个 proposal 已经迭代了 **22+ 次，全部 archived/skipped，从未交付**。这已经不是"再试一次"的问题了——引擎在反复生成一个本质上冗余的 proposal，浪费 pipeline 资源。唯一真正缺失的覆盖只有 `save_runtime_state()`、`_runtime_state_path()` 和少数 config 类（`CompactionConfig`、`SafetyConfig`、`IntakeConfig`），但 proposal 的 BAC 完全没有聚焦这些缺口，反而要求创建与现有测试重复的函数名。

## 疑虑
1. **核心前提虚假 — 测试已存在**：`tests/test_config_validation.py`（426行, ~30 测试）覆盖了 `validate_config`、`load_config`、`ValidationResult`、`ConfigValidationError`、`LLMFastConfig`；`test_spec_evo_..._config_unit_coverage.py` 覆盖了 `_find_config` 和 `_resolve_env_vars`。BAC-02 要求的三个测试函数名对应的测试逻辑已分散存在于这些文件中，新建 `tests/test_config.py` 将产生大量重复测试。

2. **22+ 轮迭代全失败 — Zombie Proposal**：两个 Scout 均确认此 proposal 已经历 22+ 次迭代，全部 archived/skipped。这意味着引擎的 proposal 生成机制对"已有覆盖的模块"产生了循环误判——静态分析显示"tests/test_config.py 不存在"→ 生成 proposal → 执行时发现重复 → skip → 静态分析再次触发。根因不在测试缺失，而在 proposal 生成逻辑的检测粒度不足。

3. **真正缺失的覆盖被忽略**：`save_runtime_state()`、`_runtime_state_path()` 完全零测试覆盖（Scout #2 确认），但 BAC 中没有一条聚焦这些函数。Proposal 错把"文件不存在"等同于"模块无覆盖"。

## 建议
1. **重构 proposal，聚焦真正的覆盖缺口**：放弃"为整个 config.py 加测试"的广度策略，改为只为 `save_runtime_state()`、`_runtime_state_path()`、`CompactionConfig`、`SafetyConfig`、`IntakeConfig` 这 5 个零覆盖符号添加测试。目标文件可以仍为 `tests/test_config.py`，但 BAC 应反映这些具体符号。

2. **修改 proposal 生成模板**：在生成"add-tests-*"类 proposal 时，不仅要检查 `tests/test_{module}.py` 是否存在，还应扫描所有 `tests/` 文件中是否已 import 并测试了目标模块的符号。避免重复生成 zombie proposal。这是根因修复。

3. **如果想统一测试入口**：如果目的确实是"将分散的 config 测试聚合到 `tests/test_config.py`"，则应在 Scope 中明确声明"迁移/整合现有测试"而非"添加"，并处理旧测试文件的清理，否则只是增加冗余。
