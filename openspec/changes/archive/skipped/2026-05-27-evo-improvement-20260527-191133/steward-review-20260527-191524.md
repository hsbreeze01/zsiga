## Verdict: PUSHBACK

## 我的判断

这个 proposal 的动机是对的——317 行的核心 runner 模块零测试覆盖确实是风险点。但 proposal 本身的质量让我无法放行。它暴露了典型的自动生成敷衍痕迹：声称要测试「公开函数」，但自己都承认函数数为 0；BAC-02 塞了个 `test_(待分析)` 占位符，BAC-03 写「至少 0 个 test 函数」——一个空文件就能满足的验收条件。这不是一个可以交付执行的工作订单，而是一份还没完成思考的草稿。我不会让 pipeline 执行一个连自己要测什么都说不清的任务。

## 评分详情
- 可行性: 2/2 -- `zsiga/harness/runner.py` 确认存在（317行），包含 10 个已验证符号（HarnessRunner、TestEvent 等），目标明确且依赖真实存在。
- 可执行性: 1/2 -- 有方向（创建测试文件、mock subprocess），但核心矛盾未解决：说要测「公开函数」却列出 0 个函数，类方法列表全为空 `methods=[]`，没有具体到「测 HarnessRunner.run() 的哪个分支」、「_HarnessCollectorPlugin 如何 mock pytest session」这样的实现路径。
- 能力匹配: 1/2 -- 无近期同类任务成功记录。历史中只有失败案例（verify-layer0-with-tests）。
- 历史风险: 1/2 -- `verify-layer0-with-tests` 在 verify 阶段失败过，模式相近（为模块添加测试），但非完全相同的失败。
- 范围合理性: 2/2 -- 范围清晰独立：只新建 `tests/test_runner.py`，明确不修改 `runner.py` 源码。
- 验收可测性: 1/2 -- 有 BAC 结构但质量不达标：BAC-02 用 `test_(待分析)` 占位符，不是可验证的符号名；BAC-03 写「至少 0 个 `def test_`」是空文件即可满足的废条件。4 条 BAC 中仅 BAC-01 和 BAC-04 有效，不满足 ≥3 条有效 BAC 的标准。
- 总分: 8/12

## 疑虑
1. **BAC-02/BAC-03 是占位符废条件**：`test_(待分析)` 不是可自动验证的符号，「至少 0 个 test 函数」等于没有要求。确定性事实显示 runner.py 有 10 个类（HarnessRunner、_HarnessCollectorPlugin 等），但 proposal 完全没指定要为哪些类/方法写测试。
2. **「公开函数」与实际结构矛盾**：proposal 反复说「为公开函数编写单元测试」，但自己给出的静态数据是「函数数: 0，类数: 10」。核心被测对象 HarnessRunner 是一个类，其方法才是测试目标，proposal 没有识别出任何方法。
3. **auto-generated 模板痕迹明显**：Constraints 明确标注「由 zsiga 自演进引擎生成」，高 CC 函数列表为空、函数列表为空、methods 全为 `[]`——这些字段本应指导测试优先级，但全是空值，说明生成器没有深入分析就输出了 proposal。

## 建议
1. **重写 BAC，绑定具体符号**：分析 `HarnessRunner` 的实际方法（如 `run()`、模块扫描逻辑 L190），为每个关键方法写出具体 BAC。例如：
   - `[BAC-02] tests/test_runner.py 中存在 def test_harness_runner_run_success`
   - `[BAC-03] tests/test_runner.py 中存在至少 5 个 def test_ 函数`
   - `[BAC-05] tests/test_runner.py 中引用了 mock 或 unittest.mock`
2. **补充类方法分析**：用 AST 提取 `HarnessRunner` 和 `_HarnessCollectorPlugin` 的所有方法签名及签名参数，作为 Technical Design 的输入。当前 `methods=[]` 不可接受。
3. **明确 mock 策略**：runner.py 用 subprocess 隔离执行 pytest（L190），测试需要决定是 mock subprocess 还是创建临时 pytest 项目做集成测试。两种路径的复杂度完全不同，proposal 必须做出选择并说明理由。
