# Design: Dashboard Auto-Refresh & Queue/Stage Real-Time Display

## Architecture Decision

**Decision**: Use a lightweight HTTP API endpoint served by the existing daemon HTTP handler, coupled with vanilla JS polling on the static dashboard page.

**Rationale**:
- The daemon already runs an HTTP server (for the current dashboard). Adding a `/api/status.json` route is minimal.
- A 10-minute polling interval is very low overhead — no need for WebSocket complexity.
- Static HTML generation remains untouched as the primary rendering path; JS overlay is a progressive enhancement.
- No new dependencies; pure stdlib (`http.server`) + vanilla JS.

## Data Flow

```
┌─────────────┐  writes   ┌────────────────────┐
│  daemon.py  │ ────────> │ daemon_state.json   │
│  (phases)   │           └────────────────────┘
└──────┬──────┘                     │
       │ scans openspec/changes/     │ reads
       │ on /api/status.json         ▼
┌──────┴──────┐            ┌─────────────────┐
│ HTTP Handler │ <──────── │ daemon_state.json│
│  /api/status │            └─────────────────┘
└──────┬──────┘
       │  JSON response
       ▼
┌──────────────────┐
│  dashboard.html   │
│  (browser JS)     │
│  setInterval 10m  │
│  fetch → DOM diff │
└──────────────────┘
```

1. **daemon.py** — during each phase transition, writes `current_change` / `current_phase` to `daemon_state.json` (already done; ensure timing is correct).
2. **HTTP handler** — new `/api/status.json` route reads `daemon_state.json` + scans `openspec/changes/*/proposal.md` to build queue.
3. **dashboard.html** — on load, renders static snapshot. JS then polls `/api/status.json` every 10 minutes and updates only the dynamic sections.

## API Contract

### `GET /api/status.json`

```json
{
  "daemon": {
    "pid": 12345,
    "state": "working",
    "cycle": 42,
    "current_change": "fix-xxx",
    "current_phase": "implement",
    "current_project": "zsiga",
    "heartbeat": "2025-01-15T10:30:00"
  },
  "queue": [
    {
      "name": "fix-xxx",
      "project": "zsiga",
      "summary": "Fix something important"
    }
  ]
}
```

- `daemon` fields map 1:1 to `daemon_state.json` fields (with safe defaults if file missing).
- `queue` is built by scanning `openspec/changes/*/proposal.md` and extracting the first `# ...` heading line.

## Key Implementation Notes

1. **HTTP handler route** — The daemon already has an HTTP server (e.g., for serving the dashboard). Add a `do_GET` branch for `/api/status.json`. Use `json.dumps()` with `Content-Type: application/json`.

2. **Queue scanning** — Walk `openspec/changes/` subdirectories. For each, read `proposal.md` and extract the first line starting with `# `. This is cheap (at most ~20 files, each <5KB).

3. **JS template injection** — The dashboard HTML template in `metrics/dashboard.py` uses f-string or string concatenation. Inject a `<script>` block at the end of `<body>` containing the fetch logic.

4. **Phase update timing** — Ensure `daemon_state.json` is written *before* the phase logic executes (not after), so the API always shows the current phase.

5. **Fallback** — The JS uses `try/catch` around `fetch`. On failure, existing static content remains visible. No error modals or alerts.

6. **No frontend framework** — Pure `document.getElementById()` + `innerHTML` or `textContent` updates. Keep it simple.

## Frontend Note

The JavaScript code embedded in the dashboard template is backend-generated (Python string in `metrics/dashboard.py`). The actual rendering logic (DOM updates, countdown timer) runs in the browser. The task to write the JS template is a **backend task** (Python string template), not a frontend task.

## Risk Mitigation

- **API not reachable** (daemon stopped): JS `catch` block prevents errors; static content shown.
- **daemon_state.json stale**: The timestamp in `heartbeat` field lets the frontend show "stale" if heartbeat is >30 min old.
- **Multiple daemons**: Not in scope; single daemon assumed.
